# OpenSearch 索引 shards（分片）与 replicas（副本）详解与最佳实践

> 面向使用 **Alauda Distributed Tracing**（Jaeger v2 + OpenSearch）的读者，讲清楚 Jaeger span 索引默认 `shards: 5, replicas: 1` 两个参数**各自的作用、对存储容量的影响，以及调优最佳实践**。全文结论均结合真实环境（`business-1` 集群，OpenSearch 3.3.1，3 数据节点）实测数据。
>
> 配置位置见本文第六章；官方调优入口：`configuration/storage-backends/opensearch.mdx#shards-and-replicas`。

---

## 一、一句话总览

| 参数 | 通俗理解 | 主要作用 | 对容量的影响 |
|---|---|---|---|
| **shards（主分片）** | 把一个索引的数据**切成几块** | 数据的**拆分、分布、并行** | **几乎中性**（切分不改变总量，仅有极小固定开销）|
| **replicas（副本）** | 每块数据**留几份拷贝** | **冗余 / 高可用 / 读扩展** | **直接乘数**：磁盘 = 逻辑数据 × (1 + replicas) |

**记忆点：分片切分，副本翻倍。** 本环境一个 span 索引 = **5 主分片 + 5 副本 = 10 个分片**，摊在 3 个数据节点上。

---

## 二、真实环境快照（作为下文依据）

### 2.1 分片分布（索引 `acp-business-1-jaeger-span-2026-07-07`）

```
shard  prirep  docs   store    node                      观察点
 0      p       129    44kb     my-opensearch-nodes-1  ┐ 主与副本在不同节点、
 0      r       129    44.2kb   my-opensearch-nodes-0  ┘ 内容/大小一致（同一份数据两份）
 3      p       86     29.5kb   my-opensearch-nodes-1  ┐ 同上，主=副本
 3      r       86     29.5kb   my-opensearch-nodes-2  ┘
 2      p       0      208b     my-opensearch-nodes-0  ┐ 空分片仍占 ~208B
 2      r       0      208b     my-opensearch-nodes-1  ┘ 固定开销（Lucene 骨架）
 1/4    ...     ...    ...      ...                       （略）
```

三点关键事实：

1. **5 主分片 + 5 副本 = 10 个分片**，一个索引就有 10 份分片实例。
2. **主分片与其副本永远在不同节点**（shard 0：主在 node-1、副本在 node-0）——这是高可用的根基：掉任一节点，每个分片的另一份拷贝仍在。
3. **副本是主分片的完整同款拷贝**（shard 0/3 的 docs 数与 store 大小主副一致）——这正是「副本翻倍磁盘」的来源。

> 注：极短窗口内主、副本各自独立 refresh，`_cat` 快照偶尔出现主副 docs 数不一致（如某分片 p=43/r=86），稍后即收敛，不影响最终一致性。

### 2.2 节点均衡（`_cat/allocation`）

```
shards  disk.indices  disk.used  disk.total  node
  37       4.2mb        52.8mb      9.9gb     my-opensearch-nodes-2
  37       3.8mb        52.2mb      9.9gb     my-opensearch-nodes-1
  38       3.7mb        52.2mb      9.9gb     my-opensearch-nodes-0
```

OpenSearch 把分片**均匀摊到 3 个节点**（各 37~38 个，这是全集群所有索引的合计，非单个索引）。

### 2.3 容量实测（来自容量评估）

| 口径 | 值 | 含义 |
|---|---|---|
| `pri.store.size` | 5,721,465 B | **仅主分片** = 逻辑数据 |
| `store.size` | 11,469,162 B | **主 + 副本** = 实际磁盘 |
| 比值 | **≈ 2.0** | 恰为 (1 + replicas) = 2 |

## 三、`shards: 5`（主分片）详解

**是什么**：索引被水平切成 5 个主分片，每个是一个独立的 Lucene 索引。每个 span 文档按 `hash(_id) % 5` 被路由到**其中唯一一个**主分片（所以 2.1 中各分片 docs 数不同，就是这样分散的；数据量大时趋于均匀）。

**作用**：

1. **分布与横向扩展**：5 块分散到多个节点，避免单节点扛下全部数据与负载。
2. **并行**：写入和查询可在 5 个分片上并行执行，提升吞吐。
3. 分片是**数据迁移、故障恢复、再平衡的最小单位**。

**对容量的影响 —— 几乎中性**：

- 切成 5 块不会让总数据变大：`5 × (逻辑数据 / 5) = 逻辑数据`。**改分片数不改变总容量**，只改变「每块多大」。
- 唯一代价是**每分片的固定开销**（2.1 中空分片 `208b`，即约 200B/分片；5 主+5 副本空索引 ≈ 1KB）。相对 GB 级数据**可忽略**。
- **单主分片大小 ≈ 每日逻辑数据 ÷ 5** —— 这是分片数的真正意义：控制单块落在健康区间。
- **主分片数在建索引时固定，事后不能直接改**（需 reindex / split / shrink）。Jaeger 每日新建索引，故调整**只对之后的新索引**生效。

---

## 四、`replicas: 1`（副本）详解

**是什么**：每个主分片额外复制 **1 份**完整副本，强制放在**其他节点**。5 主 → 5 副本 → 共 10 分片。2.1 中 shard 0 主/副 docs 都是 129、大小都 ~44kb —— **一模一样的两份**。

**作用**：

1. **高可用 / 容错**：某节点宕机，其上主分片的副本（在另一节点）会被**提升为主**，数据不丢、查询不中断。
2. **读扩展**：查询可由主或副本任一提供，分摊读压力（Jaeger UI 查询多时有益）。

**对容量的影响 —— 直接乘数，最关键**：

- **索引实际磁盘 = 逻辑数据 × (1 + replicas)**，`replicas: 1` → **2 倍**（2.3 实测 `store.size ≈ 2 × pri.store.size` 印证）。
- 落到容量评估：单 span 主 **1.3KB** → 含副本 **2.6KB**（=1.3×2）；单链、每日、常驻等含副本数字都已包含这 1 副本。
- **副本数可在线动态修改**（不像分片）：`PUT /索引/_settings {"index.number_of_replicas": N}`。
- **副本数受节点数约束**：副本不与主分片同节点，`replicas=R` 需 **≥ R+1 个数据节点**。本环境 3 节点 → 最多 `replicas=2`；设过大→副本无处安放→分片 `unassigned`、集群 `yellow`。

---

## 五、两者合起来对容量的公式

```
每个主分片大小  ≈ 逻辑数据 ÷ shards            ← shards 管「切多小 / 怎么分布」
索引实际磁盘    =  逻辑数据 × (1 + replicas)     ← replicas 管「翻几倍」
每节点占用      ≈  索引实际磁盘 ÷ 数据节点数      ← 本环境 ÷3
集群总分片数    =  Σ(每索引 shards × (1+replicas))，跨所有日期索引与索引类型累加
```

- **shards 决定分布与单块大小，不影响总量；replicas 是磁盘的直接乘数。**
- 若把当前配置的副本改成 0，所有含副本容量数字**减半**；改成 2，则 **×1.5**。

## 六、在本部署中如何修改

`shards`/`replicas` 在 Jaeger v2 的 `OpenTelemetryCollector` 存储配置中**按索引类型分别设置**（安装文档 `jaeger.yaml`）：

```yaml
# ...opensearch_storage.indices.*
indices:
  index_prefix: "${JAEGER_ES_INDEX_PREFIX}"
  spans:          { date_layout: "2006-01-02", rollover_frequency: "day", shards: 5, replicas: 1 }
  services:       { date_layout: "2006-01-02", rollover_frequency: "day", shards: 5, replicas: 1 }
  dependencies:   { date_layout: "2006-01-02", rollover_frequency: "day", shards: 5, replicas: 1 }
  sampling:       { date_layout: "2006-01-02", rollover_frequency: "day", shards: 5, replicas: 1 }
```

| 改什么 | 生效方式 | 说明 |
|---|---|---|
| **replicas（新索引）** | 改上面配置并重启 Jaeger | **次日新索引**生效 |
| **replicas（现有索引，立即）** | `PUT /<索引>/_settings {"index.number_of_replicas": N}` | 立即对已存在的当日/历史索引生效 |
| **shards** | 改上面配置并重启 Jaeger | **只对之后的新索引**生效；当日/历史索引不变（要立即改需 reindex/split/shrink）|

> 提示：`span` 是数据大头，`services / dependencies / sampling` 体量极小（实测 service 索引仅 2~3 文档、几十 KB），可给后三者更少的分片（甚至 1）以减少空分片浪费。

## 七、最佳实践

### 7.1 shards（主分片）

1. **按「单主分片目标大小」反推分片数**：业界经验单主分片 **10~50GB** 较优（过小浪费、过大恢复慢）。
   `shards ≈ 每日主分片数据量 ÷ 目标分片大小`（向上取整）。
   - 追踪场景按**峰值日增**估算（主分片口径 = 含副本量的一半）。例：日增主分片 ~80GB → `80/40 = 2`，但需兼顾节点数（见下），取 3 更合适。
2. **对齐数据节点数，保证均衡**：主分片数最好是**数据节点数的整数倍或接近**。本环境 3 节点、5 主分片分布为 2-2-1（略不均）；取 **3 或 6** 主分片分布更均衡。加副本后 10 分片分布 4-3-3，已较平。
3. **避免过度分片（oversharding）**：分片越多，堆内存 / 段 / 文件句柄等固定开销越大。经验上限 **单节点分片数 ≤ 每 GB 堆内存 20 个**。
   - 注意追踪是**每日 × 4 类索引 × (主+副本)** 累积：retention=7 天即约 `7 × 4 × 10 = 280` 个分片仅来自本项目，**retention 越长、分片数越多，集群总分片数需重点关注**。
4. **分片数不可事后改**：Jaeger 每日新建索引，天然适合「按天演进」——需要调大/调小时改配置，次日起的新索引即采用。历史索引维持原样直到被 index-cleaner 删除。
5. **给小索引更少分片**：`dependencies / sampling / services` 数据极少，5 分片纯属浪费空分片，建议单独设为 1~2。

### 7.2 replicas（副本）

1. **生产至少 1 副本**：`replicas ≥ 1` 才能容忍单节点故障不丢数据、不中断查询。`replicas: 0` 仅用于测试或可接受丢失的非关键数据。
2. **`replicas ≤ 数据节点数 − 1`**：本环境 3 节点 → 最多 2。设过大导致副本 `unassigned`、集群 `yellow`。
3. **权衡成本与可用性**：每加 1 副本 = **+1× 磁盘** + 额外写入放大（副本也要索引数据）。**`replicas: 1`（2×）是成本 / 可用的平衡点，推荐生产默认**。要求更高可用（容忍 2 节点故障）再上 `replicas: 2`（3× 磁盘）。
4. **善用「可在线调整」特性**：临时扩容/缩容、或对临近过期的冷索引降副本省空间，均可 `PUT _settings` 立即生效（追踪数据直接删除，冷索引降副本收益有限）。
5. **副本兼做读扩展**：查询密集（大量 Jaeger UI 检索）时，副本也提升读吞吐。

### 7.3 追踪场景专属建议

- **优先用「缩短 retention → 开启采样 → 降副本」控成本**：降副本(2×→1×) 立省一半磁盘，但牺牲冗余；追踪数据虽"可容忍少量丢失"，生产仍建议保留 `replicas: 1`，优先从 retention 和采样入手。
- **span 与其余索引分别配置**：把分片预算集中给 `span`，其余索引最小化。
- **容量规划以「含副本」口径下单**：采购磁盘按 `store.size`（× (1+replicas)）并预留水位余量，切勿只按主分片逻辑数据估算。

## 八、快速决策清单

| 你的目标 | 调整 | 效果 |
|---|---|---|
| 省磁盘（非关键环境） | `replicas: 1 → 0` | 磁盘减半，失冗余（不推荐生产）|
| 更高可用 | `replicas: 1 → 2`（需 ≥3 节点） | 磁盘 ×1.5，容忍 2 节点故障 |
| 单日数据量很大、分片过大 | 调大 `spans.shards` | 单分片变小，恢复/再平衡更快（次日新索引生效）|
| 集群分片过多、内存吃紧 | 调小分片数 / 缩短 retention / 合并小索引类型分片 | 降低集群总分片数与堆压力 |
| 分布不均 | 分片数对齐节点数（3 或 6） | 各节点更均衡 |

**一句话总纲**：`shards` 调**分布与单块大小**（不改总量），`replicas` 调**冗余与总磁盘倍数**；生产默认 `replicas: 1`，`shards` 按「日增数据量 ÷ 目标 10~50GB/分片、并对齐节点数」来定。
